## 次に実装する機能: 写真からの食事推定

### ユーザー体験

1. 食事追加画面に「写真から追加」を追加する。
2. カメラ撮影または写真ライブラリから画像を選べるようにする。既存のExpo SDKに合った画像選択ライブラリを使う。
3. 選択した写真をプレビューし、撮り直し・選び直し・キャンセルができる。
4. 写真を解析して、食品名・推定量（g）・推定カロリーを候補として表示する。複数品目が写っている場合は、品目ごとに編集、追加、削除できる。
5. 推定結果は自動保存しない。ユーザーが食品名、量、カロリー、食事区分を確認・修正し、「記録する」を押して初めて既存の食事記録に保存する。
6. 解析に失敗した場合も、現在の検索・手入力で記録を続けられる。
7. 画像の送信先、保存の有無、推定値であることを、利用者に分かる形で表示する。

### AI/APIと秘密情報の扱い

- リポジトリにAI APIキーや個人情報を追加しない。APIキーをアプリ内のJavaScript、`app.json`、公開GitHubの設定ファイルに埋め込まない。
- 既存のバックエンド、環境変数、画像解析サービスの有無を先に確認する。
- 既存の安全なAPI経路があれば、それを利用する。なければ、APIキーをサーバー側に置く構成を提案・実装し、環境変数名と設定方法を `.env.example` 等に記載する。`.env` と実キーはGitに含めない。
- 有料サービスの契約やAPIキーが未設定なら、ライブ解析が動くように見せかけない。先に写真選択・プレビュー・確認編集画面と、後から接続できる型付きサービス境界まで実装し、ライブ解析を有効にするために必要なサービス選択・認証情報を具体的に報告する。
- AIの回答は推定値として扱い、カロリー精度を保証しない。画像解析の結果は必ずユーザー確認を経由させる。

### 実装時の注意

- 既存の食品検索・手入力・食事区分・AsyncStorage保存との整合性を保つ。
- 食品データの由来と単位（可食部100g当たり）を維持する。
- 画像は解析に必要な範囲でのみ扱い、アプリやサーバーに恒久保存する場合は理由と挙動を明示する。
- 過剰な依存追加や画面全体の作り直しを避け、差分を小さく保つ。
- ユーザーの実データや健康情報を、公開リポジトリやログへ書き込まない。
- 依存パッケージ追加やネイティブ設定変更をしたら、開発ビルドの再作成が必要か説明する。HealthKitを含むアプリはExpo Goだけでは動作確認できない。

## 開発・実行メモ

- README記載のNode.js要件: 22.13以上。
- 依存導入: `npm install`。
- 開発サーバー: `npm start`（dev client用）。
- Expo Go用の起動スクリプト: `npm run start:go`。ただしHealthKit機能は利用できない。
- iOS開発ビルドはEASとApple署名の準備が必要。変更したネイティブ依存・プラグインは再ビルドが必要になる場合がある。
- Fast Refreshは開発サーバーと対応するアプリが起動している状態で、対応するJavaScript変更を反映する。ネイティブ構成変更はFast Refreshだけでは反映されない。
